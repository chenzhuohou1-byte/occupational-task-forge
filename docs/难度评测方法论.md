# 难度评测方法论与数据生命周期

> 面向产线协作者。本文解释两件事:
> 1. 我们怎么量一道题的难度、入库门槛为什么这么定(单发盲解 vs agent 档);
> 2. 管线会不断迭代,已有数据怎么处置——什么时候必须重测、什么时候放着不动。
>
> 可执行的权威规则在 `判分契约_v1.0.md`;本文是它背后的"为什么"。
> **本文不含任何具体任务的难度绝对数值**(公开仓纪律),只讲方法与原则。

---

## 一、盲解:我们怎么量一道题的难度

出完一道题,要知道它到底难不难,就把它丢给一个模型当"考生",**不给它看标准答案**,让它自己做一遍,再用判分器打分(0~1)。这一步叫 **N7 盲解**。"盲"= 考生看不到参考答案。

分数高 = 题太水,分数低 = 题有区分度。难度不是出题人拍脑袋写 `L1/L3`,而是**实测**出来的。

**单发盲解**和 **agent 档**是同一件事(让模型当考生)的**两种考法**,区别在于"怎么让它做"。

## 二、单发盲解 vs agent 档

| | 单发盲解 (single-shot blind) | agent 档 (multi-step with tools) |
|---|---|---|
| 怎么交互 | 整道题(全部附件+要求)塞进一个超长 prompt,模型读一遍,在**一次回答里**把全部答案写完 | 给模型文件工具(列文件/读文件/写文件/交卷),它**循环着干**:看文件→读一份→想→再读→写一部分→…→交卷 |
| 有没有工具/迭代 | 无。不能回头、不能分步 | 有。可增量读、增量写、边做边改 |
| 预算记法 | maxSteps = 1 | maxSteps = N 步(有上限) |
| 打个比方 | 闭卷,一摞材料全记脑子里,一张纸一口气写完 | 坐工位上翻文件夹,一份份看、记笔记、起草、改完再提交 |
| 贴近真实用法吗 | 否,是便宜的近似 | **是。最终 benchmark 跑的就是真 agent** |

## 三、为什么单发会"高估"难度

单发有一个和"职业能力"无关的额外负担:**一口气写不完**。附件多、要产出一大堆的题,单发模式下模型得把所有东西憋在脑子里、在一次回答里全吐出来,会"喘不过气"——token 烧光、顾此失彼。

**这部分"难"是我们考法造成的,不是这份工作本身难。** 换成 agent 档让它一份份读、一块块写,这个假难度就消失,露出题目真实难度。

实测现象(定性):一道 20+ 份附件的题,从单发换成分步后分数明显上升、露出它其实没那么难;反过来一道单发看着"过关"的软题,换 agent 档会被顶尖模型做穿——说明它真实难度不够。

## 四、门槛口径(§6.3)为什么以 agent 为准

因为**最终 benchmark 跑的是 agent**。如果用单发定门槛,我们会:
- 收进一批"单发看着难、agent 一上手就能做"的题(假难度),将来全得返工;
- 漏判一批"单发憋屈感撑成合格、其实很软"的题。

所以**入库门槛以 agent 档为准**;单发盲解降级成**便宜的预筛**(便宜模型单发就满分 → 直接退回,不必再花钱跑 agent)。

## 五、几个关键指标(别被绕进去)

- **fullPassRate (fpr,满分率)**:跑 N 次,数其中拿到满分(1.0)的占几次。`0/3` = 没一次满分 = 够难。只认满分,差一点点也算没过。
- **meanScore (平均分)**:N 次平均分,看**区分度**。两题可以都 fpr=0,但一个平均 0.2(很难)、一个平均 0.86(快做出来了、偏软)。**fpr=0 只是入库底线,平均分才看筋骨。**
- **便宜档 / 前沿档**:便宜模型 + 顶尖模型都考。连便宜的都轻松做出 → 太水退回;顶尖的都做不到满分 → 难度立得住。门槛:**便宜档 fpr 必须 = 0,前沿档 ≤ 1/3**。
- **为什么边界要补到 6 跑**:3 次只能出 0、⅓、⅔、1 四个值,前沿门槛恰好卡在 ⅓,擦线的题全看运气。规则:`fpr=0` 直接判过;`0 < fpr ≤ ⅓` 必须补到 6 跑再判。
- **maxSteps(步数预算)**:agent 档里步数就是干活预算。给少了,模型光读文件就用完、交白卷得 0——**这个 0 是假的**(我们饿死了它,不是题难)。规则:`maxSteps = 附件份数 + 交付文件数 + 50% 余量,最低 20`。
- **测量故障 vs 真难度**:上面那种假 0(单发=正文返空写 0 文件;agent=步数耗尽)必须记成**测量故障、不计进难度**,否则会把"工具卡住"误当"题好难"。

## 六、数据生命周期:管线迭代了,已有题怎么办

> 这是产线的治理原则。核心结论:**管线会一直迭代,但绝不是每迭代一次就把全库翻出来重做。**

### 先分清三类"变化",只有一部分需要动已有题

1. **管线/工具/闸门改进**(修 bug、加新闸门、改进 harness/地板)——属于**测量基础设施**。它们不会让已有测量作废,除非真的改变了某道题的得分。**绝大多数不改分。做法:老题留原地、保留它当初的验收戳;新题自然走新规则。** 像升级 linter——不会把整个代码库重排一遍,新代码守新规则,老代码等你下次碰它时顺手修。
2. **某道题自己的判分器变了**(scorerVersion 升级)——**局部**,只强制重测**那一道**。契约 §8.1 已自动处理:scorerVersion 对不上,它的旧难度数字作废。
3. **测量口径本身变了**(单发 → agent)——这是对"难度"**定义**的改动,是三类里唯一真正牵动全库口径的。但即便如此,正确做法**也不是现在重测全部**(见下)。

### 太软的题有三种回应,"加硬"只是其一、不是默认

当重测发现一道题太软:
- **重测**:只是换口径再跑一遍 N7,不改题目内容。便宜、无人工。
- **加硬**:改题目内容让它更难。贵(得重做人工内核)、产出不稳定——**只在"这道题值得留"时才做**。
- **淘汰/降级**:标成自测夹具 / SFT 素材,不再当有效 benchmark 数据。免费。

**不要反射性地加硬。** 一道软题,"退成素材 + 用新题替代"往往比反复加硬更划算。

### 治理原则:戳版本 + 懒修复 + 发布时才要求齐口径

- **每道题戳上"在哪版口径/判分器下验收"**(`measuredDifficulty` 已绑定 model/toolset/budget/scorerVersion/nRuns,基本已实现)。
- **管线迭代不触发全库回灌。** 老题带着自己的戳继续待在库里。一道题只在两种情况被重新碰:(a) 它自己的判分器变了;(b) 它要进入某个**发布快照(release)**、而该快照要求齐口径。
- **"齐口径"只在发布时、在快照内部要求,不是持续、不是全库。** 生产管线可以随便演进;必须一致的是**某次发布所用的门槛**,而每道题都记着自己过的是哪条门槛。
- 这正是 living benchmark 的做法(ALE 自己也在轮换任务、版本间换题),不是我们偷懒。

**一句话:新题走新规则;老题留原地带标签;只在"判分器变了"或"要进这次发布"时才动它。**

## 七、这次(单发 → agent 口径奠基)为什么还是要动几条

现在是特例,值得一次性做掉:**只有 4 条数据、还没发布过任何 benchmark**。趁现在把口径奠基基线理顺,比 100 条时再发现口径错了便宜得多。但即便如此,真正**被强制**的只有少数:
- 判分器本身有 bug 的(属第 2 类,和口径无关也得修)→ 修 + 升 version + 重测。
- 已经测出"太软"的 → 不是强制加硬,而是**你拍"加硬还是淘汰"**。
- 其余"目前达标、口径下待复核"的 → 可以带戳延到首次发布前再测,不必今天全backfill。
